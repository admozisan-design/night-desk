# NIGHT DESK — クラウド移行のセットアップ

NIGHT DESKのクラウドモードは**専用Supabaseプロジェクト**への接続を前提とします。
環境変数が未設定の場合は、従来のローカルデモを維持します。

## 1. 専用Supabaseプロジェクト

NIGHT DESK専用のプロジェクトを作り、東京リージョン（ap-northeast-1）を選びます。
別アプリのデータベースを使い回さないでください。作成にはユーザーによる組織選択と費用承認が必要です。

`supabase/migrations/20260930_nightdesk_cloud.sql` をこの**新しいプロジェクト**に適用します。
スキーマには次が含まれています。

- 店舗・メンバー・レコード・日次スナップショット・復元直前の安全コピー
- 店舗単位のRow Level Security（店舗外の閲覧防止）
- スタッフ（業務データ更新）と管理者（設定・メンバー・復元）の権限
- 既存の確認済みアカウントに対する管理者によるアクセス付与
- サービスロール専用の日次バックアップ処理
- データ更新のSupabase Realtime配信

Supabaseダッシュボードの Authentication > URL Configuration で
Site URLを `https://night-desk-kappa.vercel.app` に設定し、必要な認証用リダイレクトURLも登録します。
メール認証を有効にする場合は、利用するメール配信設定も確認してください。

## 2. Vercel環境変数

Vercelプロジェクト night-desk の Settings > Environment Variables に追加します。

| 名前 | 内容 | 公開 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | NIGHT DESK専用Supabase Project URL | ブラウザ可 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 有効なPublishable key（またはAnon key） | ブラウザ可 |
| `SUPABASE_SERVICE_ROLE_KEY` | NIGHT DESK専用サービスロールキー | **サーバー専用・絶対に公開しない** |
| `CRON_SECRET` | 長いランダムなシークレット文字列 | **サーバー専用・絶対に公開しない** |

環境変数を設定したら本番環境を再デプロイしてください。
サービスロールキーをGitHubや画面上の入力欄、チャットに貼り付けないでください。
Publishable keyの設定だけでは日次バックアップは動きません。

## 3. スタッフログイン

1. 管理者がログイン画面からメール＋パスワードで新規登録し、確認メールで認証します。
2. ログイン後、**新しい店舗を作成**します。そのユーザーは店舗の管理者になります。
3. スタッフも各自新規登録とメール認証を済ませ、ログイン状態でアクセス申請画面を待ちます。
4. 管理者が `設定 → クラウド・ログイン管理` でスタッフのメールアドレスを追加するとログイン可能になります。

`staff` は受付・配車・顧客・キャスト・送迎などの業務データを扱えます。
`admin` はログイン設定・料金・システム設定・CSV全置換・復元なども扱えます。
既存のスタッフ登録画面にある細かなチェックボックスと、クラウドログインの管理者/スタッフ権限は
まだ**別**です。公開運用前に必要な権限範囲を確認してください。

## 4. 旧ブラウザデータの取り扱い

**旧ローカルのデモデータや顧客データを勝手にクラウドへアップロードしません。**
クラウドモードの初回起動時に、現在のブラウザ内データの控えが
`nightdesk-precloud-local-backup-v01` としてブラウザ内に保存されます。
`設定 → 自動バックアップ` からJSONファイルとして取得できます。

必要な実データだけ、旧ブラウザで先に `設定 → CSVデータ管理` からCSV出力し、
クラウドモードに切り替えた後、管理者がCSVを取り込んでください。
旧データの誤って複数回の取込やデモデータ混入に注意してください。

## 5. 複数端末リアルタイム同期

店舗に所属したユーザーがログインすると、店舗ごとに権限分離されたレコードを取得します。
更新はコレクション内のID単位で同期し、ほかの端末にRealtimeで伝わります。
通信エラーでは「同期エラー」が表示され、操作したブラウザにはローカルの未送信データが保持されます。
接続回復後に再試行してください。

**注意:** 同一のオーダーを複数スタッフが同時編集した場合は、現状では最後の保存が優先されます。
本運用ではオーダーの競合検知・ダブルブッキング防止を追加することを推奨します。
通信が切れている間は、ほかの端末に反映済みと誤認しないでください。

## 6. バックアップ

`vercel.json` により毎日 **20:00 UTC（日本時間 翌日05:00）** に
`/api/cron/backup` が呼び出されます。
リクエストはVercel側の `CRON_SECRET` による認証が必須です。
サーバー側の `SUPABASE_SERVICE_ROLE_KEY` で
`nightdesk_daily_backup` を実行し、各店舗の全レコードを日単位で保存します。
日次保存期間は30日。管理者は `設定 → 自動バックアップ` で一覧・復元できます。
復元前の状態も独立した安全コピーに保存します。

**注意:** バックアップは同一Supabaseプロジェクト内に存在します。
データベースやプロジェクト全体の削除・障害・認証情報流出に対するオフサイト保護ではありません。
本番導入前に暗号化した外部保管またはSupabaseのバックアッププランも検討してください。

## 7. 動作確認（本番切替前）

- クラウド未設定時、旧デモ画面がそのまま使える
- 新しいSupabaseにスキーマが適用できる
- 管理者登録→店舗作成ができる
- 登録前のスタッフが他店舗・自店舗データを閲覧できない
- 管理者承認後にスタッフがログインできる
- スタッフが管理者専用画面にアクセスできない
- PC-Aで新規オーダーを登録し、PC-Bの配車ボードへ反映される
- PC-Bで別オーダーを登録してもPC-Aのオーダーが消えない
- 意図的に通信障害を起こしたとき、同期エラーが表示される
- バックアップ関数の動作確認後、復元と復元直前の安全コピーを検証する

次のステップ：Supabaseの**組織をユーザーに確認し、費用情報を提示して承認を得る**。
専用プロジェクト作成後にスキーマ適用、鍵とVercel環境変数設定、上記の実機テストを実施する。
